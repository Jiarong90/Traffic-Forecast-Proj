# 摄像头实现指南

本文档说明当前版本摄像头数据聚合、事故匹配和前端展示的实现方式。

## 1. 当前版本结论

当前事故与摄像头联动链路是：

1. 前端请求 `GET /api/incidents`
2. Node.js 拉取实时事故与实时摄像头
3. Node.js 优先调用 FastAPI `/compute/enrich-incidents-with-cameras`
4. FastAPI 在 Python 中完成事故与摄像头匹配
5. 若 FastAPI 不可用，Node.js 回退到 Python 子进程，再不行回退到 Node.js 本地匹配

## 4. 事故与摄像头匹配逻辑

### 4.1 外层接口

- `GET /api/incidents`

### 4.2 内层 FastAPI 接口

- `POST /compute/enrich-incidents-with-cameras`

### 4.3 Python 算法逻辑

在 `compute_engine.py` 中：

1. 对每个事故点遍历实时摄像头
2. 计算 Haversine 距离
3. 选最近摄像头
4. 如果最近距离超过 2000 米，则认为没有可用摄像头证据
5. 同时补充：
   - `area`
   - `spreadRadiusKm`
   - `estimatedDurationMin`
   - `estimatedDurationMax`

### 4.4 当前距离规则

1. 最近摄像头使用直线距离
2. 超过 `2000m` 不采用

这是当前“证据有效性”的限制，不是沿道路距离。

## 5. 事故标准化

事故进入系统时，Node.js 还会先调用：

- `POST /compute/normalize-incidents`

作用：

1. 统一不同来源的事故字段
2. 补齐类型、时间、位置
3. 估算影响范围和持续时间

所以当前事故链路是：

1. 标准化
2. 再做摄像头匹配

## 9. 当前容错策略

Node.js 现在采用三级容错：

1. 优先 FastAPI
2. FastAPI 失败则回退 Python 子进程
3. Python 也失败则回退 Node.js 本地逻辑

这样做的原因是：

1. 保证当前 demo 不因为单个算法进程故障而完全不可用
2. 同时逐步把计算主路径迁到 FastAPI

## 10. 已知限制

1. 当前匹配仍然是最近点策略，不考虑道路拓扑可达性
2. 2km 阈值是经验规则，不是官方阈值
3. 上游摄像头图片有效性受 data.gov.sg 波动影响
4. 若上游事故源本身无坐标或坐标异常，会影响匹配精度
